# mediasoup carries the audio; VoxLoop owns the signalling

VoxLoop's audio transport is **mediasoup**, self-hosted, driven through its first-party Rust API. mediasoup handles ICE, DTLS-SRTP, RTP forwarding and congestion control; VoxLoop writes the signalling, presence, permission enforcement and reconnection on top. v1 runs a single Worker and a single Router, with no TURN server and a single shared `WebRtcServer` port.

The [transport research](https://github.com/edwardhutchinson/voxloop/issues/3) recommended LiveKit, on the strength of it being the only candidate where every requirement was met by a first-party documented feature. That recommendation does not survive contact with the permission boundary.

**LiveKit offers two shapes and neither is the one VoxLoop needs.** Mapping a loop to a LiveKit room is the only way to get a *natively* server-authoritative boundary — VoxLoop signs a token per (user, role, loop) and the SFU enforces it without any client's cooperation. But `ForwardParticipant`, the server-side RPC for pushing one participant's audio into another room, is **not implemented in the open-source server**: the RPC is wired in `pkg/service/roomservice.go` but `pkg/service/roommanager.go:902` returns `errors.New("not implemented")`, and the proto comments it "Cloud-only". Without it, every talker needs a connection per loop they emit to and every listener a connection per loop they monitor — roughly 1,200 WebSocket and PeerConnection pairs at the pilot's scale, against a benchmark measured on a single room. The alternative shape, one flat room with per-track permissions, keeps the connection model sane but has no server-side setter: `SubscriptionPermission` can only be set by a signal message from the *publishing participant*, and the `RoomService` RPC list (`MutePublishedTrack`, `UpdateParticipant`, `UpdateSubscriptions`, …) contains no equivalent. Enforcement would then be only as honest as each publishing client, on a system whose entire purpose includes sensitive loops.

**The research's case against mediasoup was a scale argument, and the arithmetic does not support it.** mediasoup's own docs cap a Worker at roughly 500 consumers, and #3 projected VoxLoop at around 1,000. Under the topology in [ADR-0007](./0007-the-client-emits-one-stream.md) the real shape is about 40 producers and of order 3,000–4,000 consumers — higher still. But that count is of *allocated* consumers, and mediasoup's ceiling is a packet-rate ceiling. At peak only ~5 talkers are keyed, so only a few hundred forwarding paths carry packets at once: roughly 15,000–30,000 packets per second, against the 959,000 packets per second LiveKit benchmarked at 80% CPU on sixteen cores. VoxLoop's load is a few percent of a box that is already known to cope. The remaining consumers are idle, and Opus DTX ([ADR-0010](./0010-opus-mono-and-the-latency-budget.md)) makes an idle stream cost about 2.5 packets per second. *This reasoning is unverified — mediasoup's documentation does not distinguish idle consumers from active ones, and a load test should clear the allocated count before it is relied upon.*

**Pion was the serious alternative.** VoxLoop is audio-only, which is the case where writing your own SFU is most defensible: no simulcast, no SVC, no keyframes, no bandwidth-estimation drama. `pion/webrtc` still supplies ICE, DTLS-SRTP and PeerConnection, leaving offer handling and track fan-out, and the result ships as a single Go binary — a materially nicer artefact for an air-gapped on-premise install. It loses on permanence rather than difficulty: reconnection, ICE restart and RTCP handling become VoxLoop's to maintain forever, `pion/ion-sfu` has been dead since November 2022, and `pion/ion` describes itself as work-in-progress. mediasoup is the smallest step that buys the policy layer without also buying the media layer, and the media layer is where bugs are subtle, security-relevant and expensive to find.

The Rust API is not a second-class binding: the `mediasoup` crate (ISC, 0.25.2) lives in-tree at `versatica/mediasoup/rust`, releases on the same cadence as the C++ worker, and exposes the full surface this design needs — `plain_transport` for the recording seam, `pipe_transport` for cross-router growth, `audio_level_observer` for server-side verification of who is actually transmitting, and `webrtc_server` for single-port operation.

**No TURN in v1.** mediasoup bundles none, and the research scored that against it — but the case for TURN is that the *server* is unreachable, and VoxLoop's server sits at a fixed address inside the customer's network with remote users already on the corporate VPN, so ICE host candidates should simply work. One `WebRtcServer` port carries every transport, UDP primary with ICE-TCP fallback on the same port where UDP is blocked. This is a revisitable assumption, not a finding: if the pilot's VPN blocks UDP outright, ICE-TCP covers it at a latency cost we would rather discover than pre-pay for with a second daemon.

## Consequences

- **The backend is Rust.** This largely settles [Backend stack and data store](https://github.com/edwardhutchinson/voxloop/issues/13) before that ticket is worked; the remaining question there is the data store and web framework, not the language.
- **Signalling, presence, reconnection and permission enforcement are VoxLoop's code.** That is the point — the permission boundary is auditable line by line — but it is a decision surface that a product SFU would have absorbed, and reconnection in particular is not yet designed.
- **A load test must clear roughly 3,000–4,000 allocated consumers** before v1 is called done, since the argument above rests on an idle consumer being nearly free and mediasoup does not document that.
- **The single Router is a simplification, not a ceiling.** Growth is mediasoup's documented pattern — shard users across Routers, pipe producers between them with `PipeTransport` — and requires no change to the domain model, only to placement. Router-per-loop is rejected in [ADR-0007](./0007-the-client-emits-one-stream.md).
- **The mediasoup C++ worker must build and ship inside the customer's network.** One more thing for the packaging effort to carry, alongside the WebHID policy fragment and udev rule that [#16](https://github.com/edwardhutchinson/voxloop/issues/16) surfaced.
- **One inbound UDP port, with TCP on the same port.** A materially simpler firewall conversation than an ephemeral range.
