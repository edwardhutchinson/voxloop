# The operator console is two views of one loop list

> **Its deferred personalisation is settled.** Default view and manual order are personalisation scoped per `(user, role)` ([ADR-0051](./0051-personalisation-is-scoped-to-the-smallest-thing-it-is-about.md)), both persist ([ADR-0050](./0050-personalisation-persists-what-is-safe-to-be-stale.md)), a **role default** supplies their starting point ([ADR-0052](./0052-a-role-default-is-a-starting-point-never-a-floor.md)), and loop order is a complete ordering with a new loop appended and marked ([ADR-0053](./0053-the-loop-order-is-complete-and-a-new-loop-lands-at-the-end.md)). There is no "profiles" work outstanding ([ADR-0049](./0049-the-role-is-the-profile.md)).

The console renders the loops in the session's reach twice, and the operator chooses which they are looking at: the **board**, a card per loop, and the **ledger**, a compact table row per loop. Both are complete — neither is a summary of the other — and both are driven by the same presence document ([ADR-0019](./0019-presence-is-one-versioned-document-scoped-to-reach.md)), so they cannot disagree about anything except layout.

A prototype ([#12](https://github.com/edwardhutchinson/voxloop/issues/12)) built three candidates: the board, the ledger, and a third splitting the screen by *act* — what you are hearing on the left, what you would be heard on on the right. The third was the only one with a natural home for two states the model insists on, and it still lost, because the operator wants the classical board and the board is what a control room reads at a glance. Keeping both survivors was cheaper than choosing between a view that glances well and a view that reads well.

This repeats the shape of [ADR-0015](./0015-the-admin-console-reads-one-row-at-a-time.md) rather than contradicting it: there, one model turned out to need a different rendering than the matrix it was born in; here, one model needs two renderings at once. In both cases the model is the thing that survived contact with the screen, and the layout is the thing that moved.

## Consequences

- **Anything the model requires must fit in the smaller view.** A card cannot hold a sentence, so the *staffing reason* — `away — muted it`, `away — off console`, `away — not receiving it` — is a word on the board and a sentence in the ledger. This is the division of labour that justifies keeping both, and it is also the standing constraint on adding state later.
- **Ordering is shared.** Manual order and alphabetical are both offered, and reordering in one view reorders the other. Two independent orders would put the same loop third in one view and eleventh in the other, which is the quiet kind of disagreement that teaches an operator to distrust the console.
- **Default view and manual order are personalisation, not console code.** They belong with subscriptions, volumes and layout in the deferred profiles work, which owes them a model; v1 owes only the affordance.
- **Clicking a card's body toggles monitoring**, and the arm, mute and cog controls on it must not propagate that click. There is deliberately no confirmation: [ADR-0016](./0016-displayed-state-is-observed-or-asserted.md) forbids optimistic rendering, so the card will visibly lag the click, and a misclick on a loop the operator staffs announces itself immediately by dropping that loop to `away` for everyone else.
- **The loops this role staffs are marked in both views.** The safety argument above depends on the operator knowing which loops they answer for, and staffing is set per (role, loop), so it cannot be inferred from the loop list.
- **Two views is two renderings to keep honest.** Every state added to the console from here costs twice, and a state that renders in only one of them is a bug rather than a shortcut.
